# GBAX SAVX v1 — phase 3A

Independent 16 MiB persistent payload, not a change to standard 128 KiB flash. Two files of 16 MiB + 36 bytes each (about 32 MiB total at full capacity). Each holds a complete generation. Header is little-endian: magic GBAXSAV1 (8), version (4), ROM identity (4), payload size (4), generation (8), payload CRC32 (4), header CRC32 (4). CRC detects accidental corruption, not malicious modification. ROM identity is caller-supplied, intended to be a stable per-game identity (do not use a changing build CRC for future Unholy migrations).

Commit invalidates the inactive slot, syncs, writes payload, syncs, publishes header, syncs, validates readback. Never overwrites current valid slot. If interrupted after publishing a header, reopen/load to determine which generation survived. If both files are empty, initialize; if both invalid, refuse to overwrite. A first-ever interrupted commit with no valid prior generation requires explicit user recovery. Stale generation rejected. The caller must provide distinct backing files, durable sync, exclusive access, a 16 MiB payload buffer, and no truncation beyond the file format. No automatic writes or game integration in 3A. Tests simulate failure and corruption in memory; actual device filesystem durability is not yet verified.

Phase 3B will attach two VFile-backed sidecars through the Android/core save directory and provide a guest block protocol with explicit load/commit status. Only GBAX ROMs may access it. Preserve normal .sav and current SaveBlocks; actual migrations require a separate game-side versioned serializer. Do not enable automatic commits or modify save states before integration testing.

## Phase 3B: guest bridge (experimental)

For marked GBAX ROMs loaded with native save directories, the core opens per-ROM/player sidecars .savx.0 and .savx.1; normal .sav is unchanged. Identity is exact ROM CRC32 for this experimental phase: different ROM builds deliberately refuse to load each other's files. Stable game identity/migration will be a future separate protocol. Never use concurrent sessions for the same files; no cross-process lock yet. The initial adapter uses VFile sync(NULL,0), which invokes fsync on the Linux/Android FD backend. No automatic commit at shutdown or reset. Each command is synchronous and can stall the emulation thread during disk I/O. A 16 MiB transfer buffer is allocated only during a command; LOAD installs staging pages transactionally after validation. A failed/uncertain commit requires LOAD before retrying. Both sidecars must be present and writable; first interrupted save may need explicit recovery as documented above.

32-bit aligned scalar CPU MMIO registers (no DMA, LDM/STM, 8/16-bit or debugger writes): 0x44000000 ID = 0x58564153, +4 status (0 unavailable, 1 ready, 2 loaded, 3 empty, 4 committed, 0x100+backend error, 0x110 allocation failure), +8 write command (1 LOAD, 2 COMMIT), +12 generation low, +16 generation high. Read +8 returns 0. LOAD replaces exactly 0x43000000..0x43FFFFFF; other RAM is unaffected. Guest must reserve this staging region, LOAD once before editing, and explicitly COMMIT. Reset invalidates the loaded session and clears volatile RAM. Save states remain disabled. Native integration test uses real files and core bus callbacks; device QA and a guest-instruction persistence diagnostic are still pending.

## Phase 4A: GBAX named save states

Named snapshots use GBAXST01, version 1, exact ROM CRC32, exact native BIOS/version, a 128-byte bitmap, header/native CRC32 and CRC32 per nonzero 64 KiB page. Empty/zero pages are omitted. Bounds and exact file length are checked; a replacement page table is allocated and validated before restoring native state. Named slots use .xsN, separate from legacy .ssN. Loading does not write SAVX sidecars or rewind their generation; it invalidates the SAVX session, requiring explicit LOAD before another COMMIT (LOAD replaces staging RAM). Conventional battery contents, screenshot, cheats, RTC metadata and external subsystem extras are not bundled in this first named format. The fixed-size raw core API, rewind and netplay serialization remain unsupported for GBAX; no change to normal ROMs. Snapshots are not crash-atomic; keep SAVX for durable progress. Full RAM can temporarily require another 64 MiB on restore, allocation failure is handled before modifying live pages. Actual Android UI and device tests remain pending.
